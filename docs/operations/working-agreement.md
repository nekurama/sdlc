# Ways of working

**Status:** Working baseline.

## Start work deliberately

- Work from a canonical GitHub item with a clear owner, scope, dependencies, and verifiable acceptance criteria.
- Treat Ready as eligible to propose work, not permission to run an agent.
- The human owner reviews the plan and authorizes its scope before local execution, unless exact narrow pre-authorization already applies.
- Sync changes update local context and may notify the owner. Sync does not start agents.

## Keep work understandable

- State the intended outcome and constraints in the work item.
- Keep cross-team work, independently owned work, dependencies, review, or handoff visible in GitHub.
- Keep purely local execution details in Paperclip when they do not need shared coordination.
- Record material decisions and evidence so another person can understand why a path was chosen.
- Link related work instead of copying history or losing provenance.

## Execute within scope

- Use the approved plan, applicable versioned policy, work profile, and skills.
- Revalidate assignment, permission, scope, and freshness before starting and before sensitive actions.
- Stop when the scope changes materially, authority becomes unclear, or a required prerequisite is missing.
- Do not interpret retries, continuation, a green test run, or an agent's “done” as acceptance.

## Review and finish

- Submit deliverables with evidence mapped to acceptance criteria.
- The required human reviewer decides acceptance; record requested changes and rework explicitly.
- Preserve history when work is cancelled or sent back to an earlier stage.
- Complete shared work only after acceptance plus required delivery and handover conditions.
- Parent work is complete only when required child items and the parent's own criteria are complete.

## Make policies better safely

- Policies, templates, and skills are version-controlled and reviewed.
- Skills describe methods, not authority.
- Record material policy decisions with the evidence and a link to affected work.
- Treat operational feedback as linked maintenance or improvement work rather than silently rewriting history.
